What is an API?
Application Programming Interface — the waiter between two programs

🍽️ The Restaurant Analogy

  • You = the client app
  • Waiter = the API
  • Kitchen = the server / database
  • You tell the waiter → waiter tells the kitchen → kitchen sends food back

📱 You Use APIs Every Day

  • iMobile balance check → API call
  • UPI transfer → 4-6 API calls
  • Weather app → API call
  • Food delivery order → API chain

📦 The Payload is JSON

{"id": 1, "name": "Arjun",
"balance": 12500.00}

Human-readable. Machine-parseable. Universal.

Key mental model: An API is a defined contract. Two programs agree on what to ask and what to send back. You will be the person who designs and builds these contracts.

HTTP: Request & Response
Every API call follows this exact pattern — always

📤 Request (You Send)

  • Method: GET, POST, PATCH…
  • URL: /api/v1/customers/CUST1001
  • Headers: Content-Type, Authorization…
  • Body: JSON data (POST/PUT/PATCH only)

📥 Response (Server Sends)

  • Status code: 200, 201, 404…
  • Headers: Content-Type, Content-Length…
  • Body: JSON data (or empty on 204)
GET /api/v1/customers/CUST1001 HTTP/1.1
Host: api.icicibank.com
Authorization: Bearer eyJhbGci...
Accept: application/json

← HTTP/1.1 200 OK
← Content-Type: application/json
← { "customerId": "CUST1001", "name": "Arjun Sharma" }
Rule to remember: GET requests have NO body. You ask for data — you don't send data when reading. POST, PUT, and PATCH have a body.

HTTP Methods
Five methods. One purpose each.
GET — Read
POST — Create
PUT — Replace
PATCH — Update
DELETE — Remove

Three rules to live by

  • GET = read only. Never changes anything. Safe to call 100 times.
  • POST = create. Each call makes a new record.
  • DELETE = remove. Response has no body — the thing is gone.

PATCH vs PUT

  • PATCH: send only the changed fields. Safe for partial updates.
  • PUT: send all fields. Missing fields get wiped.
  • In most banking APIs → use PATCH for updates.
GET /api/v1/customers → get all customers
POST /api/v1/customers → create a customer
PATCH /api/v1/customers/CUST1001 → update fields
DELETE /api/v1/customers/CUST1001 → remove customer

Status Codes
The server talks back in 3-digit codes
200OK
201Created
204No Content
400Bad Request
401Unauthorized
403Forbidden
404Not Found
500Server Error

2xx — All Good

  • 200 = read/update succeeded
  • 201 = new resource created
  • 204 = deleted, nothing to return

4xx — Client Error

  • 400 = malformed request
  • 401 = not authenticated (who are you?)
  • 403 = authenticated but no permission
  • 404 = resource not found

5xx — Server Error

  • 500 = something crashed on our side
  • Not the client's fault
  • Our code needs to be fixed

URL Design + What is REST?
5 URL rules · 3 REST principles
1
NOUNS not verbs: /getCustomers → /customers
2
PLURAL for collections: /customer → /customers
3
LOWERCASE: /CustomerList → /customer-list
4
HYPHENS not underscores: /savings_accounts → /savings-accounts
5
NEST to show ownership: /getAccountsByCustomer?id=1 → /customers/CUST1001/accounts
📦

Resources

Think in THINGS (customers, accounts), not ACTIONS (getBalance, createAccount).

🔒

Stateless

Every request carries all the info needed. Server remembers nothing between requests.

🔧

Uniform Interface

Use HTTP as designed: GET reads, POST creates, DELETE removes. Codes that mean what they say.
